# Сериализация агрегата T-Digest: кастомный Serde для Kafka Streams

## Зачем нужен кастомный Serde

Kafka Streams реализует отказоустойчивость агрегатов через два механизма. Во-первых,
содержимое каждого state store (в данном случае хранилище `latency-tdigest` типа
`WindowStore`) сохраняется в локальной базе данных RocksDB на файловой системе
контейнера. При штатном перезапуске сервиса state store восстанавливается из RocksDB
без обращения к Kafka. Во-вторых, каждое изменение state store параллельно
реплицируется в специальный **changelog-топик** Kafka
(`monitoring-service-latency-tdigest-changelog`). При потере локального состояния
(пересоздание контейнера, миграция задачи на другой узел) Kafka Streams воспроизводит
(replay) все сообщения changelog-топика с начала, восстанавливая актуальное
содержимое state store.

Оба пути требуют сериализации объекта `TDigestAgg` в байтовую последовательность и
обратной десериализации. Стандартные Serde, поставляемые с Kafka Streams (String,
Integer, Long, ByteArray), не умеют сериализовать произвольные Java-объекты. Тип
`TDigestAgg` содержит внутреннее состояние `MergingDigest` — структуру с сотнями
центроидов — и дополнительное поле `lastTraceId`. Ни Java-сериализация (`Serializable`)
не подходит (нестабильность при обновлении версии библиотеки), ни Jackson JSON
(избыточный объём, нет специализированного десериализатора для `MergingDigest`).
Библиотека `com.tdunning:t-digest` предоставляет собственный бинарный формат
«small bytes», оптимизированный по размеру за счёт хранения только центроидов без
внутренних индексных структур. Класс `TDigestAggSerde` использует этот формат как
основу и дополняет его полем `lastTraceId`.

## Wire-формат

Сериализованное представление `TDigestAgg` имеет следующую схему:

```
┌──────────────────────────────────────────────────────────────────┐
│  4 байта  │  N байт              │  4 байта   │  M байт          │
│  tLen     │  tdigest small bytes │  traceLen  │  traceId UTF-8   │
│  (int BE) │  (MergingDigest)     │  (int BE)  │                  │
└──────────────────────────────────────────────────────────────────┘
```

- **tLen** — длина бинарного представления T-Digest в байтах, записанная как
  big-endian `int` (4 байта). Позволяет десериализатору точно выделить буфер нужного
  размера без сканирования.
- **tdigest small bytes** — N байт в формате «small» библиотеки t-digest: заголовок
  с `compression` и числом центроидов, за которым следуют попарно
  `mean` (float32) и `weight` (float32) для каждого центроида. При `compression = 100`
  и максимуме ≈ 157 центроидов размер составляет не более 157 × 8 + 12 ≈ 1268 байт.
- **traceLen** — длина строки `lastTraceId` в байтах UTF-8 (4 байта). TraceId в
  формате W3C TraceContext — 32 ASCII-символа, то есть 32 байта в UTF-8.
- **traceId UTF-8** — M байт строки идентификатора трассировки в кодировке UTF-8.

Итого типичный размер одной записи в changelog-топике: ≈ 4 + 1268 + 4 + 32 = **1308 байт**
против десятков или сотен килобайт при хранении исходного массива наблюдений.

## Ключевой нюанс: API сериализации в t-digest 3.3

В версиях t-digest до 3.2 включительно использовался метод `smallByteBuffer()`,
возвращавший готовый `ByteBuffer` с данными:

```java
// Устаревший API (t-digest ≤ 3.2) — не работает в 3.3+
ByteBuffer buf = digest.smallByteBuffer();
```

В версии **3.3** метод `smallByteBuffer()` удалён без сохранения обратной
совместимости. Правильный API разделён на два шага: сначала запрашивается необходимый
размер буфера, затем данные записываются в заранее выделенный `ByteBuffer`:

```java
// Корректный API t-digest 3.3+ — используется в проекте
ByteBuffer tBuf = ByteBuffer.allocate(digest.smallByteSize()); // (1)
digest.asSmallBytes(tBuf);                                      // (2)
tBuf.flip();                                                    // (3)
```

*(1) `smallByteSize()` возвращает точное число байт, необходимых для записи текущего
состояния дайджеста; (2) `asSmallBytes(ByteBuffer)` записывает данные по позиции
буфера, продвигая указатель position; (3) `flip()` переводит буфер из режима записи
в режим чтения — устанавливает `limit = position`, `position = 0` — что необходимо
перед передачей буфера в `out.put(tBuf)`.*

Если бы код использовал несуществующий метод `smallByteBuffer()`, приложение падало
бы с `NoSuchMethodError` при первой же попытке сериализации агрегата — то есть
спустя `windowSizeSeconds` (60 с) после старта, в момент первой операции слияния
окна. Сбой произошёл бы не при запуске, а в середине работы, что затруднило бы
диагностику: в логах было бы не «не стартует», а «работало, потом упало».

## Десериализация

```java
return (topic, bytes) -> {
    if (bytes == null || bytes.length == 0) return new TDigestAgg(); // (1)
    try {
        ByteBuffer buf = ByteBuffer.wrap(bytes);
        int tLen = buf.getInt();                                      // (2)
        byte[] tBytes = new byte[tLen];
        buf.get(tBytes);
        int traceLen = buf.getInt();
        byte[] traceBytes = new byte[traceLen];
        buf.get(traceBytes);
        return new TDigestAgg(
            MergingDigest.fromBytes(ByteBuffer.wrap(tBytes)),         // (3)
            new String(traceBytes, StandardCharsets.UTF_8)
        );
    } catch (Exception e) {
        return new TDigestAgg();                                      // (4)
    }
};
```

*(1) Пустые байты означают отсутствующую или удалённую запись в state store —
возвращается свежий агрегат, а не исключение. (2) Чтение выполняется в том же
порядке, что и запись: `tLen → tBytes → traceLen → traceBytes`. (3)*
`MergingDigest.fromBytes(ByteBuffer)` восстанавливает структуру центроидов;
пакет-прайвет конструктор `TDigestAgg(TDigest, String)` позволяет передать
восстановленный дайджест напрямую, минуя фабричный метод. *(4) При любой ошибке
разбора (повреждённые байты, несовместимая версия формата после обновления
библиотеки) возвращается пустой агрегат — Kafka Streams продолжит работу, потеряв
только данные конкретного окна, а не остановив весь стрим-процессор.*
