# Декларативная конфигурация алгоритмов обнаружения аномалий

## Архитектура класса конфигурации

Параметры всех алгоритмов обнаружения аномалий сосредоточены в единственном классе
`MonitoringProperties` (пакет `com.example.monitoring.config`). Класс аннотирован
механизмом Spring Boot `@ConfigurationProperties(prefix = "monitoring")`, который при
старте приложения автоматически десериализует дерево YAML-ключей с префиксом
`monitoring` в типизированные вложенные объекты. Явная аннотация `@Configuration`
регистрирует экземпляр класса в контексте Spring и делает его доступным для инъекции
в любой компонент системы наблюдаемости без статических полей и прямого обращения
к файловой системе.

Класс организован как трёхуровневая иерархия вложенных POJO-классов, каждый из
которых инкапсулирует параметры одного независимого алгоритма: `Latency` — расчёт
перцентилей задержки, `Dlq` — контроль частоты поступления сообщений в топик
«мёртвых» писем (Dead Letter Queue), `ConsumerLag` — мониторинг отставания
потребителя. Такая группировка предотвращает «загрязнение пространства имён»:
параметры разных алгоритмов не смешиваются и не конфликтуют при частичном
переопределении в переменных окружения Docker-контейнера.

## Описание параметров и их связь с алгоритмами

### Группа `monitoring.latency` — скользящее окно и алгоритм T-Digest

| Параметр YAML | Поле Java | Тип | Значение по умолчанию | Назначение |
|---|---|---|---|---|
| `window-size-seconds` | `windowSizeSeconds` | `int` | 60 | Длина скользящего окна (сек.) для накопления наблюдений |
| `slide-seconds` | `slideSeconds` | `int` | 10 | Шаг сдвига окна (сек.) — частота пересчёта p99 |
| `p99-threshold-ms` | `p99ThresholdMs` | `double` | 200 | Порог перцентиля p99 в миллисекундах (тип правила THRESHOLD) |
| `min-sample-count` | `minSampleCount` | `int` | 10 | Минимальное число наблюдений в окне для выдачи оповещения |

Первые два параметра определяют геометрию *скользящего окна* (Sliding Window) в
потоковом вычислителе Kafka Streams. При длине 60 с и шаге 10 с в каждый момент
обработки в окне присутствуют не более шести непересекающихся сегментов по 10 с;
старейший сегмент вытесняется при каждом сдвиге. Внутри окна значения задержки
аккумулируются через структуру данных T-Digest — вероятностный алгоритм,
обеспечивающий вычисление произвольного перцентиля с гарантированной относительной
погрешностью δ ≤ 1% при потреблении памяти O(1/δ) независимо от объёма потока.

Параметр `p99-threshold-ms` задаёт порог правила типа **THRESHOLD**: если
вычисленное значение p99 превышает порог, система формирует событие `AlertEvent` с
указанием сервиса-нарушителя, фактического значения p99, использованного порога,
временно́го окна и идентификатора эталонного трейса (exemplar_trace_id). Параметр
`min-sample-count` устраняет ложноположительные срабатывания: при малом числе
наблюдений оценка T-Digest статистически ненадёжна (высокая дисперсия), поэтому
оповещение не выдаётся вне зависимости от вычисленного значения перцентиля.

### Группа `monitoring.dlq` — частота сообщений в DLQ (правило RATE)

| Параметр YAML | Поле Java | Тип | Значение по умолчанию | Назначение |
|---|---|---|---|---|
| `window-size-minutes` | `windowSizeMinutes` | `int` | 5 | Длина окна агрегации для подсчёта частоты DLQ-сообщений |
| `rate-threshold` | `rateThreshold` | `double` | 0.01 | Пороговая доля DLQ-сообщений относительно общего потока |

Данная группа управляет правилом типа **RATE**. Kafka Streams агрегирует количество
сообщений в топике `orders.dlq` за скользящее окно `window-size-minutes` минут и
вычисляет их долю от суммарного объёма сообщений в основных топиках. Если доля
превышает `rate-threshold` (1% по умолчанию), генерируется оповещение с уровнем
`severity: warning`. Параметр `window-size-minutes` задаётся в минутах, а не в
секундах, поскольку DLQ-события — редкие и оценка их частоты требует более широкого
временного горизонта для статистической значимости.

### Группа `monitoring.consumer-lag` — отставание потребителя (правило THRESHOLD)

| Параметр YAML | Поле Java | Тип | Значение по умолчанию | Назначение |
|---|---|---|---|---|
| `threshold-messages` | `thresholdMessages` | `long` | 1000 | Максимально допустимое отставание потребителя (в сообщениях) |

Consumer lag — разность между смещением последнего записанного сообщения в партиции
Kafka и смещением последнего прочитанного сообщения группой-потребителем. Этот
параметр задаёт абсолютный порог: при превышении `threshold-messages` сообщений
компонент `ConsumerLagMonitor` публикует событие `AlertEvent` с указанием
затронутой группы, топика и партиции. Тип `long` выбран намеренно — при высокой
пропускной способности брокера lag может исчисляться десятками тысяч сообщений, и
использование `int` (макс. ≈ 2,1 млрд) было бы небезопасным сужением для
перспективных инсталляций.

## Полная YAML-конфигурация с дефолтными значениями

Листинг 1 — Полный блок `monitoring` файла `application.yml`

```yaml
# Rule parameters — change without recompilation
monitoring:
  latency:
    window-size-seconds: 60    # длина скользящего окна T-Digest (сек.)
    slide-seconds: 10          # шаг сдвига окна (сек.)
    p99-threshold-ms: 200      # порог p99, правило THRESHOLD
    min-sample-count: 10       # мин. наблюдений для подавления ложных срабатываний
  dlq:
    window-size-minutes: 5     # окно агрегации DLQ-частоты (мин.)
    rate-threshold: 0.01       # порог доли DLQ-сообщений, правило RATE (1%)
  consumer-lag:
    threshold-messages: 1000   # порог отставания потребителя (сообщ.), правило THRESHOLD
```

Все значения являются дефолтными: они продублированы как инициализаторы полей в
классе `MonitoringProperties` (строки 27, 28, 29, 33, 46, 49, 54). Это обеспечивает
корректную работу сервиса даже при отсутствии или неполном заполнении блока
`monitoring` в `application.yml`: Spring Boot применит значения из YAML поверх
дефолтов Java, а не вместо них, сохраняя часть дефолтных значений для
неуказанных ключей.

## Обоснование декларативного подхода: принцип открытости/закрытости

Вынесение пороговых значений и параметров окон в конфигурационный файл является
прямой реализацией **принципа открытости/закрытости** (Open/Closed Principle, OCP)
из набора SOLID. Согласно этому принципу, программный модуль должен быть *открыт
для расширения* и *закрыт для модификации*. В контексте системы обнаружения аномалий
это означает следующее:

**Закрытость для модификации.** Исходный код алгоритмов (T-Digest для p99, RATE для
DLQ, THRESHOLD для consumer lag) зафиксирован и не изменяется при корректировке
операционных параметров. Алгоритм обнаружения аномалий латентности не зависит от
конкретного числа 200 мс — он лишь сравнивает текущий p99 с некоторым значением
`p99ThresholdMs`, которое получает через инъекцию объекта `MonitoringProperties`.

**Открытость для расширения.** Изменение порога с 200 до 150 мс, сокращение
скользящего окна с 60 до 30 с или повышение чувствительности DLQ-правила с 1%
до 0,5% выполняется исключительно правкой `application.yml` (или переменной
окружения контейнера) и перезапуском сервиса. **Перекомпиляция исходного кода не
требуется.** Это принципиально важно в производственной среде, где цикл сборки
и тестирования Java-приложения может занимать десятки минут, тогда как оперативное
изменение порога при инциденте требует немедленного ответа.

Дополнительно Spring Boot поддерживает *иерархию источников конфигурации*: значения
в `application.yml` могут быть переопределены переменными окружения контейнера
(приоритет выше) или внешним томом с дополнительным `application-prod.yml` (профиль
Spring). Это позволяет без изменения образа Docker задавать разные пороги для
окружений разработки, нагрузочного тестирования и промышленной эксплуатации —
достаточно передать переменную окружения вида
`MONITORING_LATENCY_P99THRESHOLD_MS=150` при запуске контейнера.

Наконец, декларативный подход облегчает верификацию конфигурации: файл `application.yml`
является артефактом версионного контроля Git, его история правок отражает
эволюцию операционных решений команды, а дифф между двумя версиями однозначно
показывает, какие пороги и когда были изменены — без необходимости анализировать
исходный код или историю компиляций.
