# Алгоритм T-Digest для потокового вычисления p99 латентности

## Мотивация: O(N) против O(compression)

Наивный подход к вычислению перцентиля p99 в скользящем окне требует хранения всех
наблюдений за период окна: при 1000 спанов в минуту и окне 60 с это 60 000 значений
типа `double` (≈ 480 КБ), причём каждые 10 с после сдвига окна весь набор требует
полной пересортировки — сложность O(N log N). При росте нагрузки до десятков тысяч
RPS память state store Kafka Streams на одном узле оказывается узким местом уже на
стадии прототипа.

T-Digest (Dunning & Ertl, 2019) решает эту задачу, аппроксимируя распределение
компактным набором взвешенных центроидов. Число центроидов ограничено сверху
константой `compression` и не зависит от объёма потока: при `compression = 100`
структура данных `MergingDigest` хранит не более ⌈π · compression / 2⌉ ≈ 157
центроидов, каждый из которых занимает 16 байт (`mean: double` + `weight: double`).
Таким образом, потребление памяти составляет **O(compression)** — константу порядка
2–3 КБ — вне зависимости от того, через агрегат прошло 100 или 10 000 000 наблюдений.

| Метод | Память | Сложность добавления | Сложность квантиля |
|---|---|---|---|
| Полный массив + сортировка | O(N) | O(1) amortized | O(N log N) |
| T-Digest (MergingDigest) | O(compression) | O(log compression) | O(compression) |

## Принцип работы T-Digest

### Центроид

Центроид — элементарная структура T-Digest, характеризуемая двумя числами:

- **mean** (`μ`) — средневзвешенное значение точек, поглощённых данным центроидом;
- **weight** (`w`) — количество точек, поглощённых центроидом.

Совокупность центроидов, упорядоченных по возрастанию `mean`, образует кусочно-
постоянную аппроксимацию эмпирической функции распределения (CDF). Суммарный вес
всех центроидов равен общему числу наблюдений `n`. Для каждого центроида можно
определить его «квантильную позицию» как долю точек, находящихся левее его средней:

```
q_i = (sum_{j<i} w_j + w_i/2) / n
```

### Масштабная функция и ограничение веса

Ключевая идея T-Digest состоит в неравномерном распределении «ёмкости» между
центроидами. Масштабная функция `k(q, compression)` отображает квантильное
пространство [0, 1] на пространство индексов центроидов [0, compression/2].
Для реализации `MergingDigest` (функция k₁) она определяется как:

```
k(q) = (compression / 2π) · arcsin(2q − 1)
```

Максимально допустимый вес центроида в квантильной позиции `q` получается из
условия, что два соседних центроида не могут слиться, если их совокупный вес
превысит единицу в пространстве `k`:

```
w_max(q) = 4 · n · q · (1 − q) / compression
```

Из этой формулы следует фундаментальное свойство: при `q → 0` или `q → 1`
произведение `q · (1 − q) → 0`, поэтому `w_max → 0`. Это означает, что
**хвостовые центроиды могут поглотить лишь одну-две точки** — они представляют
отдельные наблюдения без усреднения. На хвостах распределения T-Digest ведёт
себя как точный порядковый набор, а не аппроксимация. Центроиды вблизи медианы
(q ≈ 0,5, где `q · (1 − q) = 0,25` — максимум) могут быть очень «тяжёлыми»:
один центроид поглощает большую группу схожих наблюдений, расходуя минимум памяти
на статистически неинтересную область распределения.

Наглядно: при `compression = 100` и `n = 10 000` наблюдений максимальный вес
хвостового центроида у p99 (`q = 0,99`) составляет:

```
w_max(0.99) = 4 · 10000 · 0.99 · 0.01 / 100 = 3,96 ≈ 4 точки
```

то есть каждый центроид у p99 представляет не более 4 точек, обеспечивая
**относительную погрешность вычисления p99 порядка ±0,5–1%**. На практике при
использовании `MergingDigest` с `compression = 100` ошибка квантиля 99-го
перцентиля не превышает 1–2% от реального значения при числе наблюдений ≥ 100,
что подтверждено в оригинальной статье Dunning & Ertl и независимых бенчмарках
библиотеки `com.tdunning:t-digest`.

## Метод `add(durationMs, traceId)`

```java
public TDigestAgg add(double durationMs, String traceId) {
    digest.add(durationMs);
    if (traceId != null && !traceId.isEmpty()) {
        lastTraceId = traceId;
    }
    return this;
}
```

При вызове `digest.add(durationMs)` реализация `MergingDigest` выполняет следующие
шаги. Новое наблюдение временно помещается в буфер несортированных точек. Когда
буфер заполняется (размер порядка `128 · compression` точек), выполняется операция
слияния (merge): буфер сортируется, затем точки последовательно поглощаются
существующими центроидами или создают новые, пока выполняется неравенство
`w_centroid + w_new ≤ w_max(q)`. После слияния число центроидов возвращается к
значению, не превышающему `⌈π · compression / 2⌉`.

Метод `add` возвращает `this`, что позволяет использовать его непосредственно
в лямбде агрегатора Kafka Streams:

```java
(svc, span, agg) -> agg.add(span.durationMs(), span.traceId())
```

## Метод `p99()` и алгоритм вычисления квантиля

```java
public double p99() {
    return digest.size() > 0 ? digest.quantile(0.99) : 0.0;
}
```

Метод `quantile(q)` реализован следующим образом. Пусть `n` — суммарный вес всех
центроидов, `q = 0.99`. Целевой кумулятивный вес: `h = q · n = 0.99 · n`.
Алгоритм итерирует по центроидам, отсортированным по `mean` (по возрастанию), и
накапливает кумулятивный вес `C`:

```
h = q · n

для каждого центроида c_i (по возрастанию mean):
    если C + w_i/2 ≥ h:
        # нашли центроид, содержащий целевой квантиль
        # линейная интерполяция между границами центроида
        δ = (h − C) / w_i − 0.5       # смещение относительно центра, ∈ [−0.5, 0.5]
        return mean(c_{i−1}) + δ · (mean(c_i) − mean(c_{i−1}))   # или границы центроида
    C += w_i
```

Граничные случаи: если `q = 0`, возвращается минимальное наблюдение; если `q = 1` —
максимальное. Для хвостовых центроидов, содержащих по одной точке,
интерполяция вырождается: `δ = 0`, возвращается `mean` центроида. Это даёт
точный ответ для крайних перцентилей, поскольку хвостовые центроиды однозначно
соответствуют конкретным наблюдениям.

## Поле `lastTraceId` — exemplar

```java
private String lastTraceId = "";
```

В момент, когда агрегатор определяет, что p99 превысил порог, он находится в
состоянии: «некоторое распределение точек в окне нарушает SLO». При этом T-Digest
уже не позволяет восстановить, *какое именно* конкретное наблюдение вызвало выброс —
алгоритм хранит только центроиды, но не исходные точки.

Поле `lastTraceId` реализует паттерн **exemplar** («образец»): при каждом добавлении
точки сохраняется идентификатор трассировки последнего поступившего наблюдения.
В момент срабатывания алерта этот `traceId` копируется в поле `AlertEvent.traceId`
и передаётся в Alertmanager. В Grafana ссылка на Jaeger по этому идентификатору
отображается непосредственно на панели с метрикой p99 как точка на графике с
«сноской» (exemplar marker), позволяя дежурному одним кликом перейти от
агрегированной статистики к конкретному распределённому трейсу.

Стандарт OpenMetrics (RFC 9110) формально определяет exemplar как пару
`{traceId, timestamp}`, опционально прикреплённую к метрике. В данной реализации
эта идея адаптирована к потоковой обработке: роль timestamp выполняет `firedAt` в
`AlertEvent`, а `lastTraceId` служит «лучшим доступным кандидатом» — не
обязательно самым медленным спаном в окне, но гарантированно валидным трейсом из
того же временно́го периода.

## Листинг класса `TDigestAgg`

Листинг 1 — `TDigestAgg.java`

```java
package com.example.monitoring.streams;

import com.tdunning.math.stats.MergingDigest;
import com.tdunning.math.stats.TDigest;

/**
 * Mutable aggregate for a Kafka Streams windowed computation.
 * Wraps a T-Digest (compression=100) for accurate p99 over a sliding window.
 */
public class TDigestAgg {

    private static final double COMPRESSION = 100.0;

    private final TDigest digest;
    private String lastTraceId = "";

    public TDigestAgg() {
        this.digest = TDigest.createMergingDigest(COMPRESSION);
    }

    // Package-private constructor for deserialization (TDigestAggSerde)
    TDigestAgg(TDigest digest, String lastTraceId) {
        this.digest = digest;
        this.lastTraceId = lastTraceId;
    }

    public TDigestAgg add(double durationMs, String traceId) {
        digest.add(durationMs);
        if (traceId != null && !traceId.isEmpty()) {
            lastTraceId = traceId;              // exemplar: last observed trace
        }
        return this;
    }

    public double p99() {
        return digest.size() > 0 ? digest.quantile(0.99) : 0.0;
    }

    public long size() { return (long) digest.size(); }

    public TDigest getDigest()       { return digest; }
    public String getLastTraceId()   { return lastTraceId; }
}
```

Конструктор с параметрами `(TDigest, String)` имеет область видимости `package-private`
и предназначен исключительно для использования классом `TDigestAggSerde` — сериализатором
state store Kafka Streams. Внешний код не может создать `TDigestAgg` с произвольным
дайджестом в обход фабричного метода `TDigest.createMergingDigest(COMPRESSION)`,
что гарантирует единообразие параметра `compression` для всех экземпляров агрегата.
