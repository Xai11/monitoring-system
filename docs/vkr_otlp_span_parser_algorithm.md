# Алгоритм извлечения и нормализации метрик латентности

## Структура входного OTLP JSON

OpenTelemetry Collector при экспорте трассировок через `kafkaexporter` публикует в
топик Kafka сообщения в формате OTLP JSON. Этот формат является трёхуровневым
деревом: каждое сообщение содержит массив `resourceSpans`, каждый элемент которого
описывает один ресурс (сервис) и его инструментированные диапазоны. Внутри
`resourceSpans` находится массив `scopeSpans`, группирующий спаны по библиотеке
инструментации (например, по версии OTel Java API). Наконец, массив `spans` содержит
сами спаны — единицы выполнения.

Листинг 1 — Упрощённая структура OTLP JSON-сообщения

```json
{
  "resourceSpans": [
    {
      "resource": {
        "attributes": [
          { "key": "service.name",  "value": { "stringValue": "order-service" } },
          { "key": "service.version","value": { "stringValue": "1.0.0" } }
        ]
      },
      "scopeSpans": [
        {
          "scope": { "name": "io.opentelemetry.spring-webmvc" },
          "spans": [
            {
              "traceId":          "4bf92f3577b34da6a3ce929d0e0e4736",
              "spanId":           "00f067aa0ba902b7",
              "name":             "POST /orders",
              "kind":             2,
              "startTimeUnixNano":"1718000000000000000",
              "endTimeUnixNano":  "1718000000213000000",
              "attributes": [ ... ]
            },
            {
              "traceId":          "4bf92f3577b34da6a3ce929d0e0e4736",
              "spanId":           "a2fb4a1d1a96d312",
              "name":             "orders.created receive",
              "kind":             5,
              "startTimeUnixNano":"1718000000250000000",
              "endTimeUnixNano":  "1718000000318000000",
              "attributes": [ ... ]
            }
          ]
        }
      ]
    }
  ]
}
```

Атрибуты ресурса и атрибуты спана в OTLP JSON кодируются не как объект с ключами, а
как массив пар `{key, value}`, где `value` — объект с типизированным полем
(`stringValue`, `intValue`, `boolValue` и т. д.). Это проектное решение
OpenTelemetry позволяет передавать атрибуты с разнотипными значениями в одном
массиве, однако требует линейного поиска по ключу при разборе, что и реализует
вспомогательный метод `extractAttr`.

## Пошаговый алгоритм метода `parse()`

### Шаг 1. Извлечение `serviceName` из атрибутов ресурса

Для каждого элемента `resourceSpans` парсер обходит массив
`resource.attributes` в поисках элемента с `key == "service.name"` и извлекает
значение из вложенного поля `value.stringValue`. Имя сервиса инжектируется OTel
Java-агентом через переменную окружения `OTEL_SERVICE_NAME` на старте контейнера и
гарантированно присутствует во всех спанах данного ресурса. Если атрибут не найден
(строка возвращает пустую строку), весь блок `resourceSpans` пропускается
(`continue`): дальнейшая обработка спанов без имени сервиса бессмысленна, так как
`SpanRecord.serviceName` является ключом группировки в Kafka Streams.

### Шаг 2. Фильтрация по типу спана (`kind`)

OpenTelemetry определяет пять типов спанов (SpanKind), из которых для измерения
задержки обработки запросов релевантны только два:

| kind | Константа OpenTelemetry | Назначение |
|------|------------------------|------------|
| 2    | SERVER                 | Входящий HTTP-запрос к сервису |
| 5    | CONSUMER               | Обработка сообщения из Kafka-топика |

Спаны типа **PRODUCER** (`kind=3`) намеренно отфильтрованы. Спан PRODUCER
фиксирует задержку операции *отправки* сообщения в Kafka — время от вызова
`KafkaProducer.send()` до получения подтверждения от брокера. Эта величина
характеризует пропускную способность сети и брокера, но не время бизнес-обработки
запроса. Включение PRODUCER-спанов привело бы к двойному учёту одной логической
операции: одна и та же задержка присутствовала бы и в спане PRODUCER (со стороны
отправителя), и в спане CONSUMER (со стороны получателя). Кроме того, PRODUCER-спаны
в Kafka-клиенте асинхронны и их длительность определяется параметрами батчинга
(`linger.ms`, `batch.size`), не отражая реальной задержки обработки. Спаны типа
**CLIENT** (`kind=3`... нет, `CLIENT = 3`) и **INTERNAL** (`kind=1`) также
отбрасываются: CLIENT-спаны дублируют SERVER-спаны на вызываемой стороне, а
INTERNAL-спаны представляют внутренние операции без сетевой границы.

### Шаг 3. Фильтрация служебных эндпоинтов

Спаны, имя которых содержит подстроку `/actuator` или `health`, пропускаются.
Spring Boot Actuator генерирует регулярные HTTP-запросы к `/actuator/health` от
Docker health-check и от Prometheus scrape, создавая высокочастотный фоновый
шум из быстрых спанов (1–5 мс). Их включение в расчёт T-Digest систематически
занижало бы оценку p99 бизнес-операций: при нескольких сотнях health-check спанов
в минуту даже редкие медленные бизнес-запросы могут не попасть в 99-й перцентиль.

### Шаг 4. Вычисление `durationMs` из наносекунд

Поля `startTimeUnixNano` и `endTimeUnixNano` в OTLP JSON содержат время Unix в
наносекундах с начала эпохи (1 января 1970 г. UTC). Для современных меток времени
это значения порядка 1,7 × 10¹⁸ нс, что многократно превышает диапазон типа
`int` (максимум ≈ 2,1 × 10⁹) и находится в пределах диапазона `long`
(максимум ≈ 9,2 × 10¹⁸). В OTLP JSON эти значения закодированы как строки
(не как JSON-числа), потому что ряд JSON-реализаций теряет точность при парсинге
64-битных целых в формат `double` (стандарт IEEE 754 обеспечивает лишь 53 бита
мантиссы). Метод Jackson `JsonNode.asLong()` корректно работает только для JSON-узлов
числового типа; применённый к строковому узлу он вернёт `0L` без исключения.
Поэтому значение предварительно извлекается как строка (`asText("0")`), а затем
преобразуется через `Long.parseLong()`, который интерпретирует строковое
представление числа напрямую без потери точности.

Длительность вычисляется как:

```
durationMs = (endTimeUnixNano − startTimeUnixNano) / 1_000_000.0
```

Деление на `1_000_000.0` (литерал `double`) обеспечивает получение вещественного
результата с субмиллисекундной точностью: для спана длительностью 213 нс результат
составит 0,213 мс, а не 0 (как при целочисленном делении). Дополнительная проверка
`endNs <= startNs` отсеивает некорректные записи с отрицательной или нулевой
длительностью, которые могут возникнуть при рассинхронизации часов между узлами.

## Ключевой фрагмент кода

Листинг 2 — Метод `parse()` класса `OtlpSpanParser`

```java
public List<SpanRecord> parse(String json) {
    if (json == null || json.isBlank()) return Collections.emptyList();
    try {
        JsonNode root = mapper.readTree(json);
        List<SpanRecord> records = new ArrayList<>();

        for (JsonNode rs : root.path("resourceSpans")) {
            String svc = extractAttr(rs.path("resource").path("attributes"), "service.name");
            if (svc.isEmpty()) continue;                                         // (1)

            for (JsonNode ss : rs.path("scopeSpans")) {
                for (JsonNode span : ss.path("spans")) {
                    int kind = span.path("kind").asInt();
                    if (kind != SPAN_KIND_SERVER && kind != SPAN_KIND_CONSUMER) continue; // (2)

                    String name = span.path("name").asText("");
                    if (name.contains("/actuator") || name.contains("health")) continue;  // (3)

                    long startNs = parseLong(span.path("startTimeUnixNano").asText("0")); // (4)
                    long endNs   = parseLong(span.path("endTimeUnixNano").asText("0"));
                    if (startNs == 0 || endNs <= startNs) continue;

                    double durationMs = (endNs - startNs) / 1_000_000.0;                 // (5)
                    String traceId = span.path("traceId").asText("");
                    records.add(new SpanRecord(svc, durationMs, traceId));
                }
            }
        }
        return records;
    } catch (Exception e) {
        log.warn("Failed to parse OTLP span batch: {}", e.getMessage());
        return Collections.emptyList();                                          // (6)
    }
}
```

*(1) пропуск ресурса без имени сервиса; (2) фильтр по SpanKind; (3) фильтр
служебных эндпоинтов; (4) извлечение строки с последующим Long.parseLong();
(5) вычисление длительности в мс с вещественной точностью; (6) защита от
malformed JSON — возврат пустого списка, а не исключение.*

## Обработка нерелевантных спанов в топологии Kafka Streams

Метод `parse()` не возвращает `null` для отдельных нежелательных спанов; вместо
этого он молча пропускает их через `continue` и возвращает список, содержащий
только прошедшие все фильтры записи. Пустой список является допустимым результатом
и означает, что ни один спан в данном OTLP-сообщении не был признан релевантным.

В топологии `LatencyTopology` результат `parse()` потребляется оператором
`flatMapValues`:

```java
raw
    .flatMapValues(value -> parser.parse(value))          // List<SpanRecord> → N записей
    .filter((k, span) -> span != null && span.durationMs() > 0)
```

Оператор `flatMapValues` «разворачивает» список: каждый элемент возвращённого
`List<SpanRecord>` становится отдельной записью в потоке Kafka Streams. Если
`parse()` вернул пустой список — `flatMapValues` не производит ни одной записи для
данного входного сообщения, и оно исчезает из потока без каких-либо побочных
эффектов. Последующий `.filter((k, span) -> span != null && span.durationMs() > 0)`
является защитным барьером: он отсеивает гипотетические `null`-элементы (которые
не должны появляться при корректной реализации `parse()`, но могут возникнуть при
будущих расширениях) и спаны с нулевой длительностью. Такое разделение
ответственности — фильтрация по предметной логике внутри парсера и защитный
`null`-барьер в топологии — соответствует принципу единственной ответственности
(Single Responsibility Principle): парсер отвечает за корректную интерпретацию
формата, топология — за целостность потока данных.
